# EmoGame 皮肤价值与情绪分析看板骨架

## 目标

将当前以单皮肤证据审计、模拟和数据录入为中心的 `app.py` 工作台，调整为面向业务分析师的最终分析门户。

默认使用路径为：

```text
EmoGame 分析看板
├── 组合总览（默认）
├── 皮肤探索
├── 皮肤详情
└── 数据工作台（管理入口）
```

前三个页面只负责分析和展示；现有模拟、CSV 导入、人工证据录入、校准开关、数据审计和 JSON 调试能力迁移到独立的数据工作台页面。

## 核心口径

- 现金价值、感知性价比和情绪评分是三个独立对象，不合成为一个含义不清的总价值分。
- 情绪分只使用持久化市场信号经现有 `RuleEngine` 产生的 `evaluation_score`。
- `official_prior_score` 只能标记为官方元数据先验，不能用于补齐情绪排名。
- 感知价值使用情绪评价中的 `value_for_money`，并与收藏价值、购买意愿和官方价格文本关联展示。
- 现金价值继续沿用现有优先级：人工精确值、人工估算值、CSV 上线窗口归因。
- 所有现金指标必须同时展示期间、币种、归因方法、置信度和来源。CSV 归因只能称为估算归因收入，不能表述为真实皮肤收入。
- 缺失值保持缺失，不按零处理，也不通过官方品质、价格或其他元数据自动估算。

当前本地快照有 960 个皮肤、49 条现金价值记录和 365 天收入数据，但没有持久化的 `market_signal_records` 或 `opinion_evidence_items`。首版应让皮肤目录和现金分析可用，同时为情绪分析显示明确的覆盖缺口和空状态。

## 全局导航与筛选

所有分析页面共享以下筛选条件：

- 英雄或皮肤名称搜索。
- 皮肤品质。
- 上线日期范围。
- 情绪证据状态：全部、有验证结果、缺少结果。
- 现金证据状态：全部、有记录、缺少记录。
- 分析期间。

默认分析期间以收入数据中的最大日期为结束日期并向前取 365 天，避免结果依赖应用运行当天。

界面以中文为主，采用中性的业务分析配色。证据充分、估算、缺失和风险状态使用全站一致的标签，不在主分析流程暴露数据库路径和编辑控件。

## 页面设计

### 1. 组合总览

组合总览是 `app.py` 的默认入口，回答皮肤组合规模、价值覆盖、情绪表现和现金表现四类问题。

顶部 KPI：

- 筛选后的皮肤数量。
- 具有验证后情绪分的皮肤数量和覆盖率。
- 具有现金价值记录的皮肤数量和覆盖率。
- 可按记录汇率换算为 CNY 的估算归因收入。
- 综合证据完整率。

核心图表：

- 皮肤品质分布。
- 皮肤上线事件与游戏收入时间线。
- 情绪评分与估算现金价值关系散点图。
- 证据充分皮肤的情绪分、性价比或现金价值排行。
- 情绪和现金证据覆盖缺口摘要。

只有 `validation_status == evidence_validated` 的记录可以进入情绪排行。数据不足时，图表显示缺少的记录数、字段和数据工作台入口，不使用先验值生成虚假排名。

### 2. 皮肤探索

皮肤探索页提供全量皮肤的筛选、排序和横向比较。

表格至少包含：

- 皮肤图片、英雄、皮肤名称、品质和上线日期。
- 情绪分、感知性价比分和情绪证据状态。
- 估算归因收入、销量、平均获取成本、现金置信度和归因方法。
- 综合数据完整状态。

支持按情绪分、性价比、归因收入、销量和平均获取成本排序。无值记录保留在表格中，但排在有效值之后。

比较区提供可切换横纵轴的散点图，以情绪分、性价比、归因收入、销量或获取成本作为分析轴。选择表格记录后进入对应皮肤详情。

### 3. 皮肤详情

详情页顶部展示皮肤图片、英雄、皮肤、品质、上线日期、获取方式和官方价格文本。

主体分为三块：

- 情绪分析：综合情绪分、验证状态、覆盖率、置信度、七维雷达图和缺失维度。
- 感知价值：`value_for_money`、收藏价值、购买意愿，以及与同品质皮肤的横向位置。
- 现金价值：估算归因收入、销量、平均获取成本、收入提升、期间曲线、归因方法和置信度。

页面下部展示评分与销售偏差、购买驱动力、转化阻力和建议动作。来源、计算口径、警告、证据明细和原始 JSON 默认折叠，但必须可审计。

### 4. 数据工作台

保留当前工作台能力，包括：

- 选择数据库和皮肤。
- 数据库证据、忽略证据和手动模拟模式。
- 非官方旁证和 ML 校准开关。
- CSV 收入导入与上线窗口归因。
- 人工现金价值证据录入。
- 数据审计、证据明细、方法说明和 JSON 输出。

模拟值继续只存在于会话中，不写入数据库。持久化操作必须明确标记并与只读分析页面分离。

## 数据与内部接口

新增只读 dashboard 查询层，批量读取皮肤、市场信号、评价结果、现金记录和图片信息，避免为每个皮肤反复执行 SQLite 查询。

内部读模型：

- `DashboardFilters`：搜索、品质、上线日期、情绪覆盖、现金覆盖和分析期间。
- `PortfolioSkinRow`：列表和图表所需的皮肤元数据、三类价值指标、置信度和缺失状态。
- `SkinDashboardDetail`：单皮肤维度分、现金时间序列、证据、偏差和业务建议。

查询层至少提供：

- 获取筛选后的组合摘要。
- 获取可排序的皮肤组合行。
- 获取单皮肤详情。
- 获取上线事件和收入时间序列。
- 获取证据覆盖和缺口统计。

汇总收入只纳入能够通过记录中的 FX 信息换算为 CNY 的已解析记录；无法安全换算的记录保留在详情中，但不进入组合收入总额。

保持现有 `build_payload`、现金价值写入、销售偏差、校准模型和 FastAPI 响应兼容。展示层重构不改变已有计算语义。

## 实现组织

- 将 `app.py` 改为组合总览入口。
- 在共享 dashboard 模块中集中实现查询、读模型、筛选、格式化和复用图表组件。
- 使用 Streamlit 多页面结构增加皮肤探索、皮肤详情和数据工作台。
- 将当前工作台渲染逻辑抽取为可复用管理页面，避免复制现有业务逻辑。
- 使用现有 Plotly、Streamlit 和 ECharts 依赖，不引入新的前端框架。

## 测试与验收

### 单元测试

- 批量读模型能正确合并皮肤、情绪和现金记录。
- 现金记录遵守人工精确值、人工估算值、CSV 归因的优先级。
- 币种换算、日期区间、缺失值排序和覆盖筛选正确。
- 未验证情绪结果不会进入排行榜。
- 空数据库、可选表缺失、图片缺失和无效上线日期不会导致页面崩溃。

### 页面测试

- 启动后默认进入组合总览。
- 全局筛选能同步影响 KPI、图表和表格。
- 探索页能够选择皮肤并进入详情。
- 没有情绪或现金证据时展示明确空状态。
- 数据工作台能够访问原有导入、模拟和审计能力。

### 回归测试

- 现有 `build_payload`、CSV 导入、人工现金证据保存、销售偏差和现金价值测试全部通过。
- 运行 `python3 -m unittest discover -s tests`。
- 使用当前数据库验收：目录显示 960 个皮肤，现金覆盖来自实际记录，情绪排行榜保持为空而不是由先验分补齐。

## 首版边界

- 只支持王者荣耀和本地 SQLite。
- 不增加在线 VLM 或 LLM 推理。
- 不自动估算缺失情绪分或现金价值。
- 不执行跨游戏比较和数据库迁移。
- 不将当前工作区中无关的文档修改纳入本次实现。
